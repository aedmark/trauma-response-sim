The player-facing loop, its hidden response model, and the modes that change a run.

Turn loop and endings

#
gameplayengine

Choose a response, absorb hidden stat changes, and continue until an ending condition wins.

What it does

Presents a sequence of everyday stressors. Each choice changes Repression, Social Mask, and Inner Child until a failure threshold or the mode's turn limit produces an ending.

How it works

  1. startGame() creates run state and calls loadRandomEvent().
  2. handleChoice() applies the choice effects and any unlocked mechanism modifier, clamps stats to 0–100, and updates the turn log.
  3. checkGameEnd() evaluates failure thresholds and the turn limit; otherwise the engine loads another event.

Why it works this way

The loop makes coping patterns legible through accumulated consequences rather than a single right-answer quiz. This intent is recorded in the player explanation and reinforced by D-003's hidden-effects rule.

Hidden trauma responses and mechanisms

#
gameplaymechanismsinvariant

Every choice is tagged fawn, flight, fight, freeze, or secure, but the label and effects stay hidden until after the choice.

What it does

Tracks how often the player chooses each of five response identities. Repeating one three times unlocks its coping mechanism, whose modifier affects later choices with the same tag.

How it works

Choice objects carry a tag and stat effects. handleChoice() increments the matching counter, unlocks the pack-defined mechanism at config.unlockThreshold, and adds its mod to later matching effects. The interface exposes neither the tag nor numerical outcome before selection.

Why it works this way

D-003 records the deliberate rule: choices should feel like real reactions under uncertainty, not visible arithmetic that can be optimized before clicking.

Modes, seeds, and timed events

#
gameplayrandomnessreplay

Standard, Extended Therapy, and Arcade reuse one engine while changing limits, scaling, and starting state.

What it does

Supports a finite standard run, an unlockable longer and more volatile Extended Therapy run, and an endless escalating Arcade run. Optional timed events can choose a response when the clock expires. Standard and Extended Therapy runs can replay a supplied seed.

How it works

  1. hashSeed() and mulberry32() create the run's deterministic random-number generator; in-run draws use state.rng.
  2. Mode flags select the turn limit, effect multiplier, fixed or rolled starting stats, and Arcade escalation tier.
  3. Timed events use pack-wide chance and duration values, with per-event opt-out or duration overrides.

Why it works this way

Seeds make comparisons and bug reports repeatable. The alternate modes extend replay value without creating separate engines. The shared-engine rationale is inferred from the common state and functions in js/engine.js; deterministic replay is an explicit architecture invariant.

Result sharing

#
player actionprivacy

Sharing is an explicit, on-device handoff after a run ends.

What it does

Builds a text summary or portrait image containing the ending, stats, seed, optional player name, and acquired mechanisms. The player can copy, download, or invoke the device share sheet.

How it works

Canvas helpers in js/engine.js render the image locally. navigator.share receives the generated file when supported; desktop fallback downloads it, while the text path writes only after the player requests a copy.

Why it works this way

The explicit handoff preserves the project's local-only promise while still making results portable. No result is transmitted automatically.

Case Files

#
collectionlocalStorage

A cross-run archive reveals only endings and mechanisms the player has actually encountered.

What it does

Records discovered survival-ending variants, failure-ending variants, and coping mechanisms. Undiscovered entries remain redacted.

How it works

js/codex.js stores slot indexes and mechanism keys under uct_codex_v1. A signature derived from ending-pool sizes and mechanism keys detects incompatible content-pack shapes and resets the archive instead of mislabeling old discoveries.

Why it works this way

The archive gives repeat runs a persistent collection goal without revealing choice effects or ending conditions. Numbered cases preserve D-003's hidden-information boundary.

Field Log

#
journalprotected wordinglocalStorage

A sincere journal sits beside the game but is not part of the simulation.

What it does

Lets a player record a real event, their response, body sensations, what helped, and optional response tags. It includes a notice that it is a self-tracking tool rather than therapy or crisis support.

How it works

js/field-log.js renders and stores entries under uct_field_log_v1. Its mode shares the page shell with the simulation but has separate state and a separate deletion confirmation.

Why it works this way

D-004 records that the journal is real user material: its language stays sincere, its crisis notice stays intact, and bulk game-data reset may not silently erase it.

Local state and reset boundaries

#
storagecompatibilityprivacy

All durable state lives in named localStorage keys, and the old uct_* prefix is permanent.

What it does

Persists the custom pack, Case Files, Extended Therapy unlock, Arcade score, player name, Timed Events preference, and Field Log without an account or server.

How it works

Feature modules read and write their established keys. resetAllGameData() removes simulation data after one confirmation, then asks separately whether to remove the Field Log.

Why it works this way

D-001 keeps the game serverless, D-002 preserves existing saves across the product rename, and D-004 protects journal entries from the ordinary reset path.

Content-pack contract

#
contentschemauntrusted input

One JSON-compatible structure supplies the simulator's authored content and tunable behavior.

What it does

Defines config values, zones, the five mechanisms, glitch logs, failure endings, survival endings, and events. A saved custom pack replaces the built-in default when it passes validation.

How it works

Classic scripts assemble DEFAULT_CONTENT; getContent() reads uct_custom_content_v1, parses it, and falls back to the default when contentPackProblems() finds a run-breaking structural problem.

Why it works this way

Keeping text and tuning together lets a content pack reskin the whole simulation without changing the engine. The separation follows D-001's dependency-free static architecture and the authoring contract.

Content editor

#
authoringeditor

A separate static page edits, validates, imports, exports, saves, and resets content packs.

What it does

Provides form controls for the content-pack structure and a draft workflow that can be previewed in the game after saving.

How it works

editor.html loads the content globals and js/editor.js. The editor keeps a draft in memory, writes the full pack to the shared storage key only on Save, exports JSON, and validates imported JSON before making it the current draft.

Why it works this way

Explicit Save prevents partial edits from overwriting a working pack. Keeping the editor separate from the game preserves the simple two-page static deployment. This rationale is recorded in AUTHORING.md.

Content validation and rendering safety

#
securityvalidation

Imported and saved packs are untrusted input even though the game has no server.

What it does

Rejects pack shapes that would break a run and displays pack-authored strings as text rather than executable markup.

How it works

contentPackProblems() checks required collections, known mechanism tags, numeric config and modifier values, and effect shapes. Rendering paths use textContent for pack strings; the smoke test includes a Case Files escaping check and malformed-pack fallback check.

Why it works this way

A local JSON file can still contain hostile markup or invalid values. Treating it as untrusted preserves the static app's trust boundary without forbidding community content.

Static runtime and script order

#
architectureinvariant

The game runs from file:// or any static host with no build step or runtime dependency.

What it does

Ships as plain HTML, CSS, and JavaScript. Players can open index.html directly; contributors may also use a local static server.

How it works

Classic <script> tags load shared globals in dependency order: content fragments, content assembly, Case Files, engine, Field Log, and main-page controls. The editor loads the same content base followed by its own controller.

Why it works this way

D-001 records the trade-off: universal static delivery and no dependency tree are worth relying on globals and a deliberate script order.

Verification workflow

#
testingquality

Small dependency-free checks cover pack structure, the main browser paths, documentation consistency, and this manual.

What it does

Provides repeatable checks for content validity, a seeded Chromium playthrough, JavaScript syntax, documentation references, and 3x manual structure and generation.

How it works

  1. Run node tools/check-content.js for the default and shared packs.
  2. Run node tools/smoke-test.js for the browser paths and deterministic replay.
  3. Run python3 tools/check_docs.py for the Markdown documentation set.
  4. Run python3 tools/manual.py check docs/trs.manual.json and rebuild docs/manual.html for manual changes.

Why it works this way

D-001 rules out an installed test stack, so the committed checks use platform tools and standard libraries. The 3x source is validated separately because check_docs.py checks document relationships rather than the manual schema.

SCI0 port boundary

#
toolingseparate repository

This repository owns generators for the DOS port, but not the port's generated sources or current state.

What it does

Transforms browser-game content into source material consumed by the SCI0 port in github.com/aedmark/TRS_SCI.

How it works

Node scripts under tools/ read the canonical JavaScript content and write through tools/lib/sci-paths.js into TRS_SCI_DIR, defaulting to a separate local checkout. Port outputs are committed there rather than here.

Why it works this way

The browser game is the canonical content source while SCI-specific compiled artifacts belong with the port. The exact long-term home of the generators remains open as Q-001, so this manual records the current boundary without presenting that placement as settled intent.
